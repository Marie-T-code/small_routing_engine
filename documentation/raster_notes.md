# raster notes

## Deriving a single territory DEM from two departments at different native resolutions

The routing territory (Nevers, buffered graph coverage) straddles two French departments, and IGN RGE ALTI ships them at different native resolutions: Nièvre (58) is available at 5 m, but Cher (18) only at 1 m. A DEM that spans the territory therefore cannot be a simple merge — the two sources must first be brought to a common grid. The 1 m Cher tiles were resampled down to 5 m with gdalwarp -tr 5 5 -tap -r average: -tr 5 5 sets the target resolution, -tap aligns the output grid to the target-resolution origin so both sources share the same pixel boundaries (without it, the mosaic seam carries a half-pixel offset), and -r average averages the 25 source pixels under each output pixel rather than sampling one — the right choice when downsampling elevation, since it preserves local mean height instead of picking an arbitrary point.

The two aligned sources were then mosaicked and clipped to the actual graph extent — graph_coverage (the convex hull of the graph nodes, buffered by 500 m), not a bounding rectangle — via gdalwarp -cutline -crop_to_cutline. Clipping to the real coverage rather than a bbox keeps the raster to only the ground the engine can actually route over: the final file is 4.5 MB, 7296×6987 px, EPSG:2154, altitude range 116–383 m, with 75.72% valid pixels (the remainder being the corners that fall outside the cutline).

The takeaway. The contrast with the vector sources is not that raster is harder to clean — vector data needs its own cleaning to stay homogeneous. The contrast is in how much the format decides for you. Vector hands most of the system to the tool: PostgreSQL picks the index type on its own, indexing is two lines, the format is light enough that keeping some data "just in case" costs nothing, and questions like point-lookup time or storage weight simply never surface. Raster hands all of that back. Every step is a decision the format forces you to make and own: which storage type for the pixel value (Int8/Int16/Float32 — set by the elevation range, not the CRS: 383 m rules out signed Int8 regardless of projection), and separately which CRS and resolution to store in (which is what makes -tr 5 5 mean 5 metres rather than 5 degrees, and governs grid alignment and resampling). And once stored, indexing does not happen by itself: there is even an automatic index behaviour that is silently ignored unless made explicit (learned the hard way in the tiling benchmark — see [raster_tiling_benchmark.md](raster_tiling_benchmark.md)), followed by tile-size choice driven by measured point-lookup. None of these questions exist on the vector side — the tool absorbs them. Raster forces you to think about the whole system: how it stores, how it is read, what a point-lookup costs. That is the real cost of adding a raster layer, and it is structural, not incidental to this dataset.

## CRS loss with ASCII Grid sources
The ASCII Grid format (`.asc`) does not carry the CRS in the file itself. GDAL does not infer one, and silently propagates the absence through `.vrt` and `gdalwarp`. The output is spatially correct (georeferencing, origin, pixel size all valid) but has no declared SRS — it displays fine in QGIS if you force the CRS manually, yet breaks downstream operations.
Symptom: `gdalwarp -cutline` fails with `Cannot compute bounding box of cutline. Cannot find source SRS.`. Here, "cannot compute bounding box of cutline" is the failed operation; "cannot find source SRS" is the reason. The missing SRS is on the **input rasters**, not the cutline.
Fix: `gdal_edit.py -a_srs EPSG:2154 <file>.tif` (assigns the CRS without touching pixels or georeferencing).
Lesson: when starting from `.asc`, declare the CRS explicitly (`-a_srs or -t_srs`) and verify it at each pipeline step — never assume it propagates.

## DEM output format: Int16 over Float32
Compared a 64 MB Float32 GeoTIFF against a 4.9 MB Int16 version of the same clipped mosaic. Rounding elevations to the metre caused no meaningful loss: min/max/mean/stddev are equivalent (115.8→116, 383→383, mean drift < 0.01 m), and `STATISTICS_VALID_PERCENT` is identical at 75.72% — no pixels lost. Since slope is computed as an average per edge over 20–100 m segments, decimetre precision brings no benefit at this scale.
Chose Int16 for the prototype: 14× lighter, comfortably versionable in Git.
Note: NoData was clamped from -99999 to -32768 (out of Int16 range) — downstream slope computation must use the new value.
